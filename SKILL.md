# Visual audit

Пользователь передаёт название или URL страницы, название одного или нескольких компонентов либо описание UI-сценария и один или несколько эталонов: ссылки на фреймы Figma либо изображения. Проверь страницу отдельно для каждого эталона на его фактической ширине: ширина фрейма Figma в CSS px или ширина исходного изображения в пикселях при DPR=1. Одна ссылка или картинка достаточна; если переданы три, проверь все три. Не подставляй фиксированные брейкпоинты и не ищи дополнительные адаптивы самостоятельно. Результат — самостоятельный HTML-отчёт с визуальными доказательствами и простым списком замечаний. Не исправляй страницу, не составляй отдельный план исправлений. Не сопоставляй слои Figma с DOM, не собирай computed styles для аудита: проверка визуальная.

## Новая проверка

Каждый новый запрос на проверку, включая повторную проверку после правок, запускай с нуля в новом уникальном каталоге запуска (например, дата-время и случайный суффикс). Заново получи текущие эталоны из Figma либо используй исходные изображения, указанные пользователем для этой проверки; заново сними текущую страницу для каждого эталона, выполни сравнение, визуальный анализ и сформируй новый HTML-отчёт.

Не используй старые actual.png, diff.png, overlay.png, comparison.json, issues.json, отметки reviewedViews или report.html как результаты новой проверки. Не копируй прежние замечания без повторного подтверждения на новых снимках. Ссылку пользователю выдавай только на отчёт текущего запуска. Старые отчёты сохраняй отдельно; при сбое новой проверки сообщи о сбое, не подменяй её старым отчётом.
## Подготовка

1. Прочитай проектные инструкции. Если пользователь указал страницу, найди её маршрут и рабочий URL. Если указаны только названия одного или нескольких компонентов либо UI-сценарий, создай временную моковую страницу в приложении проекта для скриншотов. **Не используй Storybook**, его stories, iframe или сервер для такой проверки. При необходимости запусти dev server штатной командой проекта. Если цель проверки неоднозначна, уточни только недостающие сведения.

   Моковая страница должна подключать реальные компоненты проекта, его глобальные стили, шрифты, плагины и необходимые провайдеры. Собери указанные компоненты вместе и воспроизведи нужный сценарий через props, слоты, локальные фикстуры и действия пользователя; используй prepare.mjs для действий перед снимком. Сохрани контекст размещения по эталону: контейнер, фон и окружающие элементы, необходимые для проверки. Не переписывай компоненты и не меняй их оформление ради совпадения с макетом. Снимай моковую страницу на ширине каждого эталона и укажи её URL в config.json.

   Используй отдельный временный маршрут без добавления в меню приложения. Зафиксируй в notes состав моковой страницы, состояние и фикстуры. Перед созданием страницы проверь существующие изменения; после съёмки удали только созданные для этого аудита временные файлы и изменения, сохранив пользовательские правки и артефакты отчёта.
2. Для каждой переданной ссылки через доступную Figma-интеграцию определи конкретный фрейм и его ширину по метаданным. Для изображения прочитай размеры исходного файла, а не экранного превью. Обрабатывай только переданные эталоны; не выбирай соседние фреймы и не требуй недостающих адаптивов. Применяй обязательные навыки Figma перед соответствующими инструментами, если они этого требуют.
3. Для Figma получи оригинальный PNG каждого переданного фрейма **в масштабе 1x**. Не используй уменьшенное превью MCP и не растягивай изображение. Если интеграция отдаёт точный PNG/файл — сохрани его доступным способом. Если отдаёт только визуальное превью, используй `export-figma.mjs` с `FIGMA_TOKEN` из окружения. Не извлекай токены из чужих конфигов и не выводи их. Если токена нет и инструмент не даёт оригинал — попроси настроить токен или предоставить PNG. Не считай превью эталоном. Переданное изображение используй в исходном размере; если формат отличается от PNG, преобразуй в PNG без изменения ширины и высоты. Для готовых изображений Figma-интеграция и токен не нужны.
4. Прочитай [формат запуска и замечаний](references/workflow.md), создай config.json вне директории скилла и новый каталог запуска. Добавь отдельную запись views для каждого эталона с уникальным id, даже если ширины совпадают; width равен ширине этого эталона. Для изображения figmaUrl не нужен. Все команды выполняй через абсолютные пути к скриптам этого скилла. Зависимости из его собственного package.json, а не из проекта: при отсутствии выполни `npm ci` в каталоге скилла. На Windows при установленном Microsoft Edge добавь `"channel": "msedge"` в config.json — этот вариант не требует загрузки Chromium. Иначе используй Chromium Playwright, при отсутствии установи через `npx playwright install chromium`. Уважай разрешения среды. Отдельный Playwright MCP не нужен.

## Съёмка и сравнение

- Ширина окна равна ширине текущего эталона, DPR=1. Высота окна по умолчанию 900 px и задаётся отдельно через viewportHeight; при явной другой высоте первого экрана в задании используй её. Запиши использованные параметры. Высота полного фрейма или изображения не равна высоте браузерного окна.
- Перед съёмкой договорись о видимом состоянии по макету: начальный экран, открытое меню и т. п. Если нужны действия или фикстуры, используй небольшой локальный `prepare.mjs`; запиши действия в `notes`. Не скрывай баннеры/текст, не меняй CSS оформления и данные только ради уменьшения diff. Несовпадение контента фиксируй как ограничение, не как доказанную CSS-ошибку.
- Выполни `capture.mjs <config.json>`, затем `compare.mjs <run-directory>`. Скрипт открывает изолированный браузер, ждёт шрифты/картинки, прокручивает страницу, возвращается наверх и проверяет стабильность последовательных скриншотов. Ограничение — 30 000 px высоты страницы и 100 шагов прокрутки; превышение требует конечного состояния страницы, а не обрезки аудита.
- Прочитай `comparison.json`, включая warnings. Проверь глазами, что открылась нужная страница, нет загрузчика/логина/ошибки, текст и изображения загрузились. Предупреждения и ограниченную воспроизводимость явно отрази в отчёте. Не объявляй успешный аудит по одному pixelmatch.

## Визуальный анализ

Для каждого эталона открой оригиналы design.png и actual.png, затем diff.png/overlay.png. Для длинных страниц просмотри **все** полосы `tiles` из comparison.json, особенно низ страницы. Полосы имеют исходный масштаб и перекрываются на 100px; `y` — координата начала в полном изображении. При мелких деталях используй `crop.mjs`, чтобы рассмотреть область без уменьшения всего широкого снимка.

Сравни наличие/порядок блоков, размеры и положение, переносы текста, визуальную типографику, цвета, рамки, радиусы, изображения и их кадрирование. Игнорируй только обоснованный шум растеризации, а не целые текстовые области. Процент diff — диагностика, не порог приёмки. Отсутствие красных пикселей не заменяет осмотр.

Пиши наблюдаемые различия: «заголовок в три строки вместо двух». CSS-причину формулируй только как гипотезу: «проверить размер шрифта и ширину». Не угадывай точные шрифты/значения CSS по картинке. Группируй каскадные смещения от одного дефекта. Сохраняй различия общего положения при рассмотрении отдельных секций.

Заполни issues.json по схеме из references/workflow.md: где, что отличается, необязательная короткая подсказка и прямоугольник доказательства. Для исчезнувшего блока выдели ближайшее место его ожидаемого расположения на actual и сам блок на design. Только после полного просмотра эталона и снимка страницы добавляй его id в reviewedViews. Замечания привязывай к viewId, чтобы различать эталоны одинаковой ширины. Непросмотренный эталон не равен «ошибок нет».

## Отчёт

Запусти `report.mjs <run-directory>`. Получится `report.html` с встроенными изображениями, работающий без сервера: переключатели эталонов с указанием ширины, рядом/наложение/разница, масштаб, карточки, выделения и крупные фрагменты. Кнопка копирования передаёт замечания другому агенту. JSON остаётся рядом.

Открой отчёт в доступном браузере, проверь переключатели, отображение отмеченной области и отсутствие обрезанного содержания карточек. Дай пользователю ссылку на HTML, кратко назови число замечаний и ограничения съёмки. Не добавляй план исправлений. Не отправляй отчёт во внешние сервисы без запроса.
